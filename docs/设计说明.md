# Vnav 设计说明

这份文档记的是**为什么这么做**，不是做了什么。功能清单在 README 里，部署步骤在 [`部署说明.md`](../部署说明.md) 里。

写它的原因很实际：这个项目里有几处地方改到第三、第四稿才对，有些坑（比如 `backdrop-filter` 会让 `position: fixed` 的子元素改变参照系）不写下来，下次还会踩。所以每一节都尽量带上「否掉的方案」和「当时的实测数据」。

---

## 一、它是什么，不是什么

一个自托管的浏览器起始页：打开浏览器第一眼看到的那个页面，把常用站点按分类摆好，点开即走。

**它不是一个「导航站产品」。** 没有广告位、没有收录申请、没有运营后台、没有多租户。它是给一个人或者一个小团队自己用的东西——所以它可以长得很安静，不需要用醒目的色块去抢点击。

这条定位决定了很多细节：卡片可以做得克制（白底细边框，不投影）、分组可以做成目录（不需要「推荐」「热门」这种运营位）、搜索框可以放在正中（因为它是这个页面唯一的高频动作）。

**技术上的唯一硬约束**：一个 PHP 目录 + 一个 SQLite 文件。不能要求用户装 Docker、不能要求 MySQL、不能有构建步骤。所有设计都要在这个约束下成立——比如图标必须落盘成本地文件（不能依赖 CDN）、字体必须自托管、CSS 必须是手写的。

---

## 二、页面的三段结构

顶栏、左侧分类栏、主区卡片网格。三段之间必须有明确的边界，否则整页会糊成一块。

**边界靠什么**：顶栏常驻一条 1px 底线（不是滚动后才出现）、侧栏是独立的一列面（比主区深 3%，右侧一条竖线、无圆角无投影）、主区只有卡片。

**为什么侧栏不能做成圆角卡片**：做过一版，侧栏浮在页面中间、带圆角和投影。结果是它和主区的卡片在视觉上是同一种东西——都是「浮起来的白块」，只是大小不同。用户读不出「左边是目录、右边是内容」这个层级。改成整列到底之后，它变成了一条「面」，层级立刻成立。

**为什么侧栏要能收起**：240px 在 1440 屏上占了六分之一。不是所有人每天都用分类导航——有的人就靠搜索和「常用」。收起后只剩 68px 的图标条，主区跟着铺开。宽度变量 `--hp-nav-w` 同时被侧栏宽度和主区左内距读，一处改动两边生效，不会出现「侧栏收了但正文还空着一块」。

## 三、卡片为什么是横向的

图标在左，标题和描述在右，单卡 84px 高、272px 宽、4 列。

**改之前的方案是竖向**：图标在上、标题在中、域名在下。单卡长到 108px，一屏只能看两行（14 条），224px 的宽度里只有一行短标题，剩下大片空白。

那不是配色问题，是**密度问题**。眼睛扫一列图标是横向动作——竖向堆叠等于逼着视线每张卡都往下走一次再回到顶部。改成横向之后，一屏从 7 条变成 15 条，而且「图标 → 标题」这个阅读动线是连续的。

**圆角收到 8px**：72–84px 高的卡片配 12px 圆角，圆角占高度 17%，看着偏软。8px 是 11%，利落得多。经验值：圆角超过高度的 15% 就会显得「软」。

**静止不投影**：静止态叠阴影在浅色底上只会让白卡发灰、整页显脏。层次靠 1px 边框，投影只在悬停和浮层出现。

**密度不能靠缩小**：试过把卡片压到 187×60、5 列、7px 间隙——数字更密，但发碎，读起来更累。密度要靠卡片内部排版（横向、单行）解决，不是靠整体缩小。

## 四、颜色是数据，不是样式

每个分组有一枚固定色相：常用是金、AI 是紫、开发是蓝、设计是粉、资讯是青、影音是红、效率是橙。

**绑语义，不绑序号**。按分组在列表里的位置配色看着更「自动平衡」，但分母是分组数量——删掉一组，后面所有组的颜色集体前移。用户刚记住「紫色是 AI」，第二天它变成了资讯的颜色，那这套颜色就不再是信息，只是噪音。

**颜色要贯穿**：侧栏图标块 → 组标题前的图标块 → 选中行的底色和左侧短条 → 卡片悬停时边框里掺的那一点组色。只在一个地方上色，它仍然是装饰；串起来之后，「紫色那栏 = 紫色那组」这条对应关系才成立，颜色才成为导航线索。

**侧栏图标为什么破例用实色**：卡片图标是 95% 亮度的淡底 + 深色图标，很克制。但 28px 的块里，15px 描边图标的彩色面积不到 3%，淡底在灰侧栏上看着仍然是灰的。要让「一列彩色」真的成立，只能让色块本身是实色。全站只有这一处这样做，它反而成了识别度最高的地方。

**参数调过一轮**：第一版饱和度 84%、亮度 63%→51%，黄色和青柠在白描边下面会「发亮」——白线压在亮黄上几乎没有对比度，缩小看是一团糊。压到 78%、60%→48% 才立住，其余色相只是从「糖果」变成「墨水」。

## 五、编辑模式的四个不可回退的决定

编辑态是整页换一套语言：卡片边框变虚线（草图语言，提示「这些卡现在能被拎起来」）、左上角出现勾选框、底部浮出批量操作条。

拖拽排序的实现里有四条是踩过坑之后定死的，改回去一定会坏：

**1. 落点用「直接挪卡片」，绝不用占位线。**
占位线自己占一个网格单元，多列下会把所有参照系推偏——实测症状是同一行内从左往右拖，指示线永远黏在自己屁股后面不动。

**2. 拖动全程用起手那一刻的矩形快照判定，不每次 `getBoundingClientRect()`。**
因为一边拖一边真挪 DOM，实时读到的坐标是「已经排好之后」的，拿它反过来决定排到哪儿，逻辑上是自证，界面会抖。

**3. 绝不在手势进行中改 `touch-action`。**
浏览器会直接抛 `pointercancel`。触摸端走的是另一条路：按住不动 260ms 起拖（这段时间浏览器认定是长按、不起滚动），起拖后再由 JS 加内联样式接管手势。260ms 是调过的——短于 200ms 误触太多，长于 350ms 又要等得明显。

**4. 拖动时选中卡片必须传 `noScroll`。**
`scrollIntoView` 会触发平滑滚动，触摸端的手势立刻被浏览器判给滚屏，表现为「手指按在卡片上拖，页面却在滚，卡片纹丝不动」。

**为什么把手最后被删掉了**：原本卡片左上角有个六点拖动把手。但整张卡片本来就能拖（鼠标 6px 阈值、触摸长按 260ms），把手只影响「从哪儿起手」——它解决的是一个不存在的问题。而编辑时真正频繁的动作是「一次改十条」，所以那个位置换成了勾选框。

**批量删除为什么破例弹确认框**：单条删除靠 toast 上的「撤销」兜底，批量删除没有对应的恢复接口。一次删掉二十条，没有二次确认就等于把不可逆的动作押在一次误触上。

## 六、图标：为什么预置数据不带图

新装的站点自带 9 个分组、67 条常用站点。这些数据的 `icon` 字段是空的。

图标是各家站点的 favicon，**商标归各站点所有**，不适合跟着 MIT 授权一起分发。而且它本来就是抓一次就有的东西——装完之后在后台点一次「补图标」，几十秒就齐了。

**搜索引擎的图标是另一回事**，用的是各家官方 logo 的本地文件。这里有个教训：早期手绘过一组近似标记，看起来「差不多就行」，实际上一眼就能认出「这不是 Google 的 G」，反而更廉价。越是天天见的品牌越经不起近似，外面那层彩色方块也一并去掉——那是给近似图形补辨识度用的，官方 logo 自带配色。

⚠️ 切换引擎时搬的是 `img.src`，不是 `<svg>`。换成 img 之后，`querySelector('svg')` 恒为 null，搬运步骤会静默跳过，按钮永远停在首屏那一个，**不报错、不抛异常，只是什么都不做**。

## 七、性能：能省的都省了

**服务端渲染，零构建。** 没有打包步骤，改完直接刷新。CSS 手写，没有框架。代价是不能用 JSX/SCSS，好处是任何人拿到源码都能立刻改。

**输出压缩**：Brotli 优先，其次 gzip 6，小于 1KB 不压，必须带 `Vary` 头。首页从 108 KB 压到 16 KB。

**零第三方请求**：字体、图标、引擎 logo 全部本地化。这不只是隐私问题——很多自托管场景根本没有外网，页面不能因为拿不到 Google Fonts 就排错版。

**首屏 HTML 做过一次体积优化**：游客分支里大量 `<?php if ($admin): ?>` 不成立，会留下成片的空格缩进，实测占原始体积的一半。加了一层只对首页开启的 HTML 空白折叠（API 的 JSON 绝不能走这条路）。

## 八、踩过的坑（清单）

**CSS 相关**

- **`backdrop-filter` 会让元素成为 `position: fixed` 子元素的包含块。** 搜索框挂了磨砂后，引擎下拉（fixed + JS 算 left）的 `left:476px` 变成「相对搜索框」，渲染到 952px、整块飞出半屏。要挂磨砂又要有 fixed 子元素，只能二选一。同样要小心 `transform`、`filter`、`will-change`、`contain: paint`。
- **`position: sticky` 的 top 是相对「最近的滚动祖先」算的。** 换布局容器时，吸顶标题会被推下一整个顶栏高度、正好压在第一行卡片上。换皮肤最容易漏的就是这类「定位与滚动上下文」继承。
- **`height: 100%` 在 grid 项目上会形成尺寸循环。** 行高 auto + 子元素 100% 互相依赖，浏览器按循环处理，百分比失效、退回固有比例。改 `position: absolute; inset: 0` 才定住。
- **grid item 上的 `margin: 0 auto` 会让 stretch 失效。** 一条 `max-width + margin: auto` 在普通流里无害，一旦变成 grid item，auto margin 把宽度收成内容宽度并居中——主区缩到 471px、卡片挤成单列。
- **简写属性会重置你没写的部分。** `padding: X Y` 会把 `padding-left` 一起清掉，把侧栏让出的通道抹平。
- **磨砂玻璃只在「有内容从下面穿过」时成立。** 静态浅色背景上 blur 一块纯色，得到的还是纯色，只留下一条灰带。顶栏必须静止透明、滚动后才出现。
- **组标题不要铺横带。** 要遮内容就得有不透明底色，而底色是渐变，任何纯色块盖上去都会比周围深或浅。正确解法是别吸顶。
- **`border-style: dashed` 单独写没用。** 虚线必须比实线更深才成立——实线只要「有一条界」就够，虚线的信息全在断点上，沿用静止态那层 8% 的灰，等于没做。
- **同特异性、后加载者赢。** `.gnav-mtoggle { display: none }`（桌面隐藏）写在 media query 之后，把窄屏的 `display: flex` 一起覆盖掉了，手机上触发条根本不显示。

**JS 相关**

- **`dataset` 只认 `data-*` 转换后的驼峰键。** `dataset['data-theme-set']` 恒为 `undefined`，读属性要用 `getAttribute`。
- **`requestAnimationFrame` 里读不到同步写入的布局。** 需要两次 rAF 或者读一次 `offsetHeight` 强制回流。
- **拖动与点击要分离。** 同一张卡既要能「点开改」又要能「按住拖」，必须设阈值（鼠标 6px）；否则手一抖就把一次点击变成一次排序，还会误存。
- **`<a href>` 天生 draggable。** 编辑态下必须显式 `draggable="false"`，否则浏览器启动原生拖放，会把 `pointermove` 截流，自己的拖动永远收不到事件。

**PHP / SQLite 相关**

- **建表语句和迁移语句要一致。** `CREATE TABLE` 里没有的列（靠后来的 `ALTER` 加的），如果建表结尾又把 `schema_version` 写成最新，「版本落后才迁移」这条判断就永远不成立——新库会缺列，而所有查询都在 `WHERE user_id = ?`。这类 bug 只在「全新安装」时出现，带着旧数据库升级永远不会暴露。
- **写接口一律带归属条件。** `UPDATE ... WHERE id = ?` 在 id 唯一时不会改错行，但漏掉 `AND user_id = ?` 等于给以后埋一个越权口子。
- **`rowCount() === 0` 要当失败处理。** 否则越权操作会「谎报成功」。
- **SQLite 的 WAL 模式需要目录可写**，不只是文件可写。权限不对时报的是 `attempt to write a readonly database`，不是「权限不足」。

**协议与交互**

- **MIT 协议不能写「保留所有权利」。** 那句话与 MIT 直接冲突。开源项目的页脚只需要「年份 + 作者 + 协议名」，协议名链到 LICENSE 全文。
- **隐藏（`hidden` 属性）和 `display: flex` 会打架。** `[hidden]` 自带的 `display: none` 会被同元素的 `display: flex` 覆盖，必须显式写一遍 `.x[hidden] { display: none }`。
- **fixed 浮层要补正文底部留白。** 不补的话滚到页面最底下时，浮层正好压住最后一行内容，那一屏永远看不全。

## 九、目前没做的

- 普通账号在前台切换皮肤只写 localStorage，没有同步到账号
- 后台没有用户管理页（注册开关已埋但没 UI）
- 默认数据没有独立的编辑入口（管理员日常编辑的就是这份）
- 「批量添加」（一次粘贴多行 URL）没做

这些不是遗漏，是还没想清楚该以什么形态出现。
